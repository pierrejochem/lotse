# 134. `lotse mcp`, a separate command for AI agents

- Status: Accepted
- Date: 2026-11-22

## Context

Operators and developers want to hand parts of their work with a cluster to an AI agent: look at its health and lag, create a stream or a queue, produce a few records and read them back. The Model Context Protocol (MCP) is how agents reach such tools. The agent must act as the person who signed in, and the cluster must judge each request exactly as it judges the same request over the native protocol; an agent that could do more than its user would be a hole in tenants and roles (ADR 0039, rule 8 of AGENTS.md). Credentials must not travel in plain text off loopback (rule 7). Access tokens (ADR 0133) give an agent a credential that stops by itself.

## Decision

- **A separate command.** `lotse mcp` speaks MCP and talks to the cluster through `lotse-client`. The broker gains no HTTP or JSON-RPC surface. The tools live in the crate `lotse-mcp`, generic over the `lotse-rt` traits and free of transports, so a simulation runs them against real nodes; `lotse-node` adds the transports through `rmcp`, the official Rust SDK (3.11.0), which serves MCP 2026-07-28 (stateless, `server/discover`) and 2025-11-25 for clients that still open a session. Tools only: no resources, prompts, sampling or tasks.
- **Reaching the cluster.** `--config` (addresses and CA from the cluster file) or `--bootstrap host:port,...` with `--ca`. Always TLS; plain TCP only with `--plaintext-on-loopback` to a loopback address, as the runtime enforces.
- **Stdio.** One principal for the process, from `LOTSE_TOKEN`, from `LOTSE_USER` and `LOTSE_PASSWORD`, or from a client certificate (`--cert`, `--key`). Without one it exits 2 and names them. It signs in at start, waiting up to 15 s: a bad credential or an unreachable cluster ends it with exit 1 before any tool is offered. Standard output carries only JSON-RPC; logs go to standard error (`LOTSE_LOG`).
- **Streamable HTTP.** With `--listen host:port`, one endpoint, `POST /mcp`. Plain HTTP only on loopback; elsewhere `--tls-cert` and `--tls-key` make it HTTPS, else it exits 2. The process holds no credential of its own and refuses to start with one. Every request carries its own: `Authorization: Bearer <access token>` or `Basic <user:password>`; no credential or a failed sign-in gets 401 with `WWW-Authenticate`, and no tool runs.
- **One client per credential.** The process keeps a signed-in client per credential, keyed by its SHA-256, never the credential. A client is closed after 15 minutes unused; at most 1,000 are held and the least recently used goes first. Sign-ins in progress do not count toward the 1,000 and cannot evict a working client; at most 256 credentials wait or sign in at once and at most 32 sign-ins reach the cluster at once. A request that cannot start its sign-in within 5 s gets 503 with `Retry-After: 1`. A cluster that cannot be reached also gives 503.
- **A revoked credential fails at once.** Before a cached client serves a request it makes a `WhoAmI` call, so a revoked or expired token fails on its next request, at the price of one round trip per request. A changed password is another matter: a cached client keeps working until its session ends, so after rotating a password a cluster admin revokes the user's sessions (`RevokeSessions`, ADR 0070). That also ends every token the user made before it, for good (a token's session counts from its creation), while `DescribeTokens` and `list_tokens` still list those tokens until they expire; new ones must be made.
- **Browsers.** A request with an `Origin` header is refused unless `--allow-origin` lists it as `scheme://host[:port]`. There is no CORS preflight support, so in practice browsers are refused. `null` is refused at start; a value with a path or a trailing slash can never match and is warned about. The HTTPS certificate is read at start and not reloaded. `rmcp`'s `Host` check is on for plaintext loopback and off under TLS, where the certificate's name and the `Origin` check protect against DNS rebinding.
- **Tools.** Twenty-three: look (`cluster_overview`, `list_resources`, `describe_stream`, `describe_queue`, `describe_consumer_group`, `node_metrics`, `list_sessions`, `describe_upgrade`), data (`read_stream`, `produce`, `publish`, `list_offsets`), change (`create_stream`, `create_queue`, `declare_exchange`, `bind`, `unbind`, `alter_configs`, `create_partitions`), destroy (`delete_resource`, `purge_queue`, `requeue_dead_letters`) and tokens (`list_tokens`). Each is one or a few client calls as the signed-in principal, with a JSON schema; a result carries `structuredContent` and a short text. A destroying tool needs `confirm` equal to the resource's name and is marked `destructiveHint`. `alter_configs` is marked `destructiveHint` too; it asks for `confirm` only when a setting can delete data ([ADR 0135](0135-alter-configs-asks-for-confirm-when-a-setting-can-delete-data.md)). `list_sessions` gives a token's id as `token_id` in the form `list_tokens` uses for `id`, 16 lowercase hex digits. A refusal or failure of the cluster comes back as a tool result with `isError` and the broker's message, not as a protocol error. A `describe` of something several nodes answer shows a part that was refused as not shown and a part that failed as an `*_error` field, so a gap is never read as zero. `lag` is to the last stable offset (`lag_against` says so), `lag_to_high_watermark` sits beside it.
- **Data limits.** `read_stream` reads committed records, at most 100 or 1 MiB of raw record bytes (base64 output can reach about 1.4 MiB); a key, value or header that is not UTF-8 comes back in base64. `produce` takes at most 100 records.
- **Left out.** No tool takes messages from a queue: a consumer that reads takes them out of flight for others, which an agent should not do by accident; `describe_queue` shows what waits. Making and revoking tokens is not a tool; it stays in the console and the clients, and `list_tokens` only lists. There is no MCP OAuth flow.
- **A rule for the future.** A new feature's plan includes its tools in `lotse mcp`, shipped in the same change with tests; a feature without tools says why in its ADR (AGENTS.md, *Conventions*).

## Consequences

- The broker's surface stays as it is; `lotse mcp` can run on a developer's machine, as one shared process, or in a container, and a fault in it never touches a node.
- Every tool call is judged by the cluster as the signed-in principal's own request. `lotse mcp` has no rights to lose or leak, and a shared process serves each request only with the client of the credential it carried.
- An HTTP deployment is one more process to run and to make highly available; two behind a load balancer need nothing shared, as no session is kept.
- A `WhoAmI` per request costs a round trip. It is what makes revocation immediate, and it is accepted.
- Tools are a surface to maintain: each feature that changes a request changes its tool, and the rule above makes that part of the work.
- The tool list grows with the features; the guide's list and `docs/status.md` say what exists.

## Rejected

- **MCP inside every node.** A node with `mcp = "host:port"` would be integrated and as available as the cluster, but the broker would gain an HTTP and JSON-RPC surface and a dependency on an MCP library in the process that holds everyone's data.
- **MCP in the console.** The least new code, as the console already holds a client per user; but the console is optional and runs on one machine, and a developer who wants a tool on a laptop would need a console.
- **MCP's OAuth authorization flow.** An authorization server and dynamic client registration are a product of their own. Agents sign in with an access token or a password in a header or an environment variable.
