# 50. Rebalancing groups onto new nodes

- Status: Accepted
- Date: 2026-10-30
- Supersedes in part: [ADR 0048](0048-adding-and-removing-nodes.md) (a node never returns to a group it left; a node link only from a listed node)

## Context

After ADR 0048 a new node took new groups and the replicas of drained nodes, but nothing moved existing groups onto it: a cluster grown from three nodes to five kept all its old partitions on the first three. Leadership was wherever elections left it, so one node could lead most groups and carry most of the writes. And a node never held a group again once it had left it: a replica rejoining under the same id with an empty log could vote twice in a term it had already voted in. With groups moving to even out load, that rule soon left no node a group could move to.

## Decision

**Replicas move automatically, by count, with a threshold** (maintainer's choice). While no node drains, the metadata group's leader moves one replica at a time from the node with the most replicas to the one with the fewest, choosing a runtime group that has the first and not the second and is not moving already, with at most four groups moving across the cluster (the same limit as a drain). It stops when the fullest and the emptiest node differ by at most one replica or a tenth of the fullest. A move is an ordinary `SetVoters`, carried out by the group's leader as in ADR 0048. The measure is the replica count: bytes and traffic vary faster than a move takes.

**Leaders spread too** (maintainer's choice). Every node computes, from the same metadata state, a preferred leader for each group: one of its voters, so that each node is preferred for as few groups as can be, the lowest id among equals. A leader whose group is settled and not moving hands leadership to the preferred voter with Raft's leader transfer, only once that voter has every entry, at most one handover per node every 100 ticks and per group every 1,000.

**A moved replica keeps its term and vote** (supersedes ADR 0048's rule that a node never returns to a group it left). Once a move off a node has settled, the node removes the group's log and snapshot but keeps its hard state, with the commit index at 0. Should the group come back, the new replica starts from that term and vote, so it never votes twice in a term; the planner may place any group on any active node again. It also records the decision that moved it, and until the replica holds a membership newer than that decision it grants no vote: before the move it may have acknowledged entries it no longer has, and a candidate with an older view of the group (one that restarted with a log ending before the move) could otherwise win with its vote and overwrite them. Once it holds the membership that placed it there again, its log holds everything committed before, and it votes like any other replica. A node removes a moved replica only if the replica's own membership is not newer than the decision that moved it: a node whose view of the metadata group lags (after a restart, say) would otherwise wipe a replica the group had since placed there again, which may be a voter that commits rest on.

**Raft ignores answers from before a member joined.** A member's progress records the first replication round sent to it as a member; an answer to an earlier round came from an earlier incarnation of that node (before it was removed and its replica wiped) and is ignored. Without this, a late acknowledgement from the old replica made the leader count the new, empty one as caught up. And a learner that answers with less than it acknowledged (its replica was made anew) starts over from what it has; learners count toward no commit, and otherwise the leader never sent it anything below what it had acknowledged.

**A lagging node asks for the node list** (maintainer's choice; amends ADR 0048's link rule). A node that restarts with an old view of the metadata group may not list a node added since. If that node now leads the metadata group, the lagging node refuses its link and has no address to answer it at, so it never catches up. So a node whose metadata group has no leader, or one it does not list, asks for the node list every 100 ticks (`DescribeNodes`, which nodes may now send, answered by the metadata leader through a node it lists), links to the nodes it is missing, and takes from them only the metadata group's frames until its own metadata state lists them.

## Consequences

- A new node fills up without anyone asking, and leadership follows; a cluster settles within one replica (or a tenth) per node.
- Every move copies a group in full through Raft, so growing a cluster costs network and disk on the old nodes until it settles; four groups move at a time.
- The count ignores size and traffic: a node can hold as many replicas as the others and still carry more bytes. A measure by size would need what this one avoids, a figure that changes while groups move.
- A node that was down while its replicas moved off it removes them when it next applies the moves, not before.
- A node not yet listed by a lagging node can reach it, but only for the metadata group; every other group still hears only listed nodes.
- Tests: planner unit tests (a new node gets replicas until the nodes are within one, nothing moves while a node drains or when nearly even, preferred leaders spread, leadership goes only to a preferred voter that has everything, a node that left a group may hold it again, a replica placed back stays while the node lags); node tests that a moved replica leaves only its term, its vote and the record of the move, reopens empty with that term, and grants no vote until it holds a newer membership; Raft tests that an answer from before a node rejoined does not count and that a learner that lost its log catches up again; a node test that a node not listed yet is heard only for the metadata group. The membership simulation checks after the drain that replicas are even, no node leads more than two of the four partitions, and no node keeps the log of a group it is not a voter of. The simulation found the five bugs above (a late answer, a wiped replica's vote, a lagging node wiping a replica placed back, a learner that lost its log never catching up, a lagging node never reaching a new metadata leader); a sixth was in the simulation itself, which read the voters from the removed node, still running with what it last knew. Every rule was broken on purpose and a test failed.
