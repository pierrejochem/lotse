# 55. Dead-letter queues and message TTL

- Status: Accepted
- Date: 2026-11-01

## Context

Queues deliver at least once and count deliveries on requeue and ack timeout (ADR 0031), but nothing acts on the counts: a message that always fails is delivered for ever, and a message nobody wants never goes away. The design document plans dead-letter queues and TTL (`TIMER` records, a timer wheel). Moving a message to another queue crosses two Raft groups, which can be led by different nodes and fail independently, so "exactly once" needs a design of its own. Replicas must agree on what was dropped without consulting their own clocks.

## Decision

**Settings are per queue** (maintainer's choice), given to `CreateQueue` (`configs` and the `dlq` field) and changed at runtime with `AlterConfigs`, read with `DescribeConfigs`, like the ack timeout (ADR 0035). Keys: `max.deliveries` (1 to 65,535), `message.ttl.ms` (above 0) and `dead.letter.queue` (the name of a queue). All are off by default, so existing queues behave as before. A key is reset by deleting it. Runtime queues only; configured queues take the settings from `QueueConfig` (`limits`, `dead_letter`). The metadata record and snapshot formats change (`VERSION` 4, snapshot `FORMAT` 11); like every format change in the first cuts there is no migration.

**A delivery attempt** is a delivery that did not end in an ack: a nack with requeue, an ack timeout, or a connection that closed with the message in flight. The first two are persisted (ADR 0031), a disconnect is counted in the leader's memory. A message goes out at most `max.deliveries` times as the leader counts; the next time it would go out it is retired instead. Counts are a lower bound (a failover forgets the in-memory part), so a message may in fact be delivered more often after failovers, never fewer times than the header says. Reason: the counts already exist and cost no extra writes. Since ADR 0109 every delivery's count is in the log, so a failover no longer forgets any.

**Retiring is decided by the leader and written to the log.** Replicas never look at a clock or a count of their own. Leader steps:

1. **Claim.** The leader proposes a `RETIRE` batch (new batch kind 5) naming the messages, their reason and delivery count, and the dead-letter queue. Applying it settles a message that is still unsettled and records that it is *owed* to the dead-letter queue (snapshot state). An ack and a claim are ordered by the log: whichever applies first settles the message, the other changes nothing. So a message acknowledged before the claim is never dead-lettered. Without a dead-letter queue the claim is an ordinary ack: **the message is dropped**, settled like an acknowledged one. Reason: the maintainer's default; the alternative, keeping it for ever, is what the limit exists to end. Trade-off: data loss by configuration, so set a dead-letter queue when messages matter.
2. **Forward.** The leader reads each owed message from its own log and sends it with the internal `DeadLetter` request (API key 44, nodes only) to the dead-letter queue's leader, through the same client path as transaction markers. The copy keeps key, value and headers and gains headers `x-lotse-dead-letter-reason` (`max-deliveries` or `expired`), `-queue`, `-queue-id`, `-offset`, `-deliveries` and `-floor`; earlier such headers are replaced, so the headers describe the latest move.
3. **Done.** Once the dead-letter queue answers (the copy is committed there), the leader proposes a second `RETIRE` batch that clears the debt.

**Exactly once across failover.** The copy goes into the dead-letter queue as a batch of the new kind `DeadLetter` (4), which only the broker can write (`Produce` still accepts data only). Every record names its source queue id and offset. Each replica of the receiving queue keeps, per source queue, the source offsets it has taken, and when it applies a batch it settles a record whose source and offset it has taken before, so that record is never delivered. A repeated send (after a timeout, or from a new leader that finds the debt in the applied state) therefore changes nothing. The set is pruned by the `floor` each record carries: the source's retention floor, below which nothing is owed any more; a late copy from a deposed leader below it is recognised as a repeat. The debt is in the replicated state, so no message is lost: a leader that dies between any two steps is replaced by one that starts from the applied state. The data of an owed message stays in the log (retention stops at the lowest owed offset).

**Message TTL** counts from the time the leader of the queue appended the message: a queue with a TTL has its produced batches stamped with the leader's wall clock (`Clock::unix_time`) before they are proposed, preserving the distances between records, so a producer's clock does not matter. Messages written before the TTL was set keep their producer's timestamps. The leader scans from the ack floor for expired batches whenever the head may have expired (at most every quarter TTL, between 10 and 500 ms) and claims them with reason `expired`. A message in flight with a consumer does not expire; a message that is released again is subject to the TTL. The unit of expiry is the batch (its latest record's timestamp), so a message never expires early. Replicas do not decide: they apply the claim. In addition, the delivery step itself refuses to send a message past its TTL or past `max.deliveries`, whatever the scan has found, so such a message is never delivered after the leader could have known. Trade-offs: the leader's clock and a failover matter. After a failover the new leader does not know what its predecessor had in flight, so it may expire a message that a consumer still holds; that consumer's later ack finds it settled, and the message is also in the dead-letter queue (at-least-once). Since ADR 0109 the new leader knows from the log which messages are with a consumer and leaves them. Transactional messages age from the time they were appended, not committed, and expire at once on a commit after the TTL.

**A dead-letter queue that is missing or deleted.** It must exist and be a queue when the setting is made. A queue named as someone's dead-letter queue cannot be deleted (`INVALID_REQUEST`; the delete is also ignored when applied, so a concurrent change cannot break it). If a debt names a queue deleted nevertheless (the setting was changed, then the queue deleted), the debt is dropped. If the queue is merely unavailable, the leader retries every 200 ms and the message stays owed.

**Cycles.** A queue cannot be its own dead-letter queue, and a setting that would lead back to the queue through other queues' dead-letter queues is refused; both when the request is checked and again when the metadata record is applied.

**Tenants.** The dead-letter queue must be in the tenant of the queue (checked on the metadata leader and again when applied); `DeadLetter` is accepted only from nodes (or on a cluster without authentication, like markers) and the receiving node checks that source and receiver belong to the same tenant. A user needs the admin role on the queue to change its settings, as for the ack timeout; nobody can write a `DeadLetter` batch with `Produce`.

**Known limits.** A message too large to carry the extra headers in one batch is dropped instead of forwarded. A move is not atomic with the consumers of the receiving queue: they see the copy as soon as it is committed there. Settings of configured queues come from the node configuration (not the cluster file; there are no resources in it). No metrics for retired messages yet.

## Consequences

- Poison messages and stale messages leave the queue by themselves, to a queue where operators can inspect and requeue them.
- Every retired message costs a claim, a forward and a done batch; queues without limits cost nothing extra.
- Retention of a queue with a dead-letter queue is held back by messages not yet forwarded; if the dead-letter queue is down for long, the source log grows.
- Mutation-checked: the delivery threshold, the order of ack and claim, the repeat recognition (and its floor), the retention floor, the expiry threshold and the delivery-time TTL check each have a test that fails when the rule is broken; leaving a debt in place never clears it, which the simulation notices as a run that does not end.
- The queue simulation (`tests/queues.rs`, same CI job) has a second scenario with queues `poison`, `drop`, `short` and `graveyard` under crashes and partitions.
