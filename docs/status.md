# Status and known gaps

## Status

Preview: release 0.1.0 is the first ([its notes](releases/0.1.0.md)), 0.1.1 the latest, a release of the console ([its notes](releases/0.1.1.md)); 0.2.0 is being built ([its notes](releases/0.2.0.md)). The runtime seam with its Tokio implementation, the record format, the segmented log, the Raft core, the simulation harness, a broker node (many Raft groups over one transport) and the first cut of the native protocol with a Rust client (idempotent and transactional produce, read_committed fetch, queues with acks, credit and redelivery, publishing through exchanges, consumer groups with exactly-once consume-transform-produce, a metadata group that creates, changes and deletes streams, queues and exchanges at runtime), TLS 1.3 on every connection with node certificates, authentication (client certificates, SCRAM-SHA-512, OAUTHBEARER), tenants and six roles checked on every request exist and are tested, and so does the management console, with OpenID Connect sign-in, against a real cluster (numbers from `DescribeMetrics`, which every node answers for itself) or a built-in demo cluster. Retention deletes whole segments by age and size (streams) or below the ack floor (queues), and streams can be compacted to the newest record per key. The `lotse` binary runs a node from a cluster file, under systemd, OpenRC or sysvinit from a `.deb`, `.rpm`, `.apk` or tarball, or as a container image or a Helm chart on Kubernetes, all from a reproducible release build; nodes can be added to and drained from a running cluster, and a cluster upgrades one node at a time without stopping.

## Known gaps

Three kinds, most urgent first: weaknesses that can bite today, things not built yet, and limits that were decided (the ADR says why).

### Weaknesses

- **Groups without a leader on loaded machines:** tests against real nodes failed now and then on CI runners because a group answered `NOT_LEADER` or delivered nothing for seconds: a node's rounds outlasted the election timeout, then 100 to 200 ms, and the fast followers of every group it led elected again. A node now persists its groups together (ADR 0143), and groups elect after a second by default (ADR 0144), so stalls of a few hundred milliseconds keep their leaders. A stall longer than the election timeout still costs leadership. Each group still syncs its own log and rewrites its hard state for every commit; one log for all groups on a node would make it one sync, and heartbeats sent while a round persists would make a slow disk cost no leadership at all. Skipping the commit-only hard-state writes cut stalls further but let a restarted node answer `UnknownStream` from a metadata state behind its log, so it waits until a node no longer answers from a state it knows is behind. Nodes log their groups' elections and their loop's stalls (ADR 0139), and CI turns that on, so a further failure shows where the time went.

### Not built yet

- **Certificates and sessions:** a notice to the CA holder other than the `/metrics` gauge and the console's count; OCSP; revoking a node certificate other than through the CRL file; sessions are revoked per user or IdP group, not per token (ADR 0070; a token is revoked alone with `RevokeToken`).
- **Access tokens** (ADR 0133): a token carries every role bound to its owner's own name and cannot be narrowed to less; it carries no IdP groups, so a user whose roles all come from groups gets a token that grants nothing; the lifetime is one of five steps (7, 30, 90, 180 or 365 days) and cannot be extended, only replaced. Tokens made before their owner's `RevokeSessions` are refused at sign-in but still listed (`DescribeTokens`, the console, `list_tokens`, `lotse_tokens`) until they expire; the console and the SDKs show a token's id as a decimal number, `lotse mcp` as 16 hex digits.
- **MCP** (ADR 0134): `lotse mcp` has no OAuth authorization flow (agents sign in with an access token or a password); no tool takes messages from a queue or makes or revokes tokens; browsers are refused (`--allow-origin` lists origins, but there is no CORS preflight); the HTTPS certificate is read at start and not reloaded; a changed password keeps working on a cached client until its session ends, so revoke the user's sessions after rotating one, which also ends every token the user made before it for good; a revoked token may get 503 instead of 401 when two `WhoAmI` answers are lost (it corrects itself on a retry); a publish refusal carries no broker reason. Tools so far: 23 (look, data, change, destroy, list tokens); the list grows with each feature, by the rule in AGENTS.md.
- **Metadata:** a stream's partitions only go up (ADR 0074); streams from the node configuration take the node's defaults and cannot be changed at runtime, and only runtime streams can be compacted.
- **Kubernetes:** the Helm chart (ADR 0128) runs the node list it was installed with; adding or removing nodes there is a manual procedure. Every pod mounts every node's key, and the operator endpoint is reachable only inside each pod, so Prometheus cannot scrape it. The operator that does these is proposed, not built (ADR 0129). The node certificates name the pods, not the client Service, so clients bootstrap at the pods' names. The chart's console (ADR 0137) keeps its session key and chart history in its pod, so a restarted pod signs users out.
- **Console** (ADR 0137): it reads its HTTPS certificate at start, so a renewed one needs a restart, as `lotse mcp --listen` does.
- **SDK packages** (ADR 0142): released with the broker to GitHub Packages and as files on the GitHub release, where downloading from GitHub Packages needs a GitHub token even for public packages. Maven Central, nuget.org and npm are prepared but not switched on: they need accounts, secrets and, for Maven Central, a verified namespace for `dev.lotse`. An SDK fix alone needs a release of everything. The packages are not signed; `SHA256SUMS-sdk` and reproducible builds are the checks.
- **Packages:** they are not signed: `SHA256SUMS` and a reproducible build are the checks (ADR 0126), and Alpine installs the `.apk` with `--allow-untrusted`. sysvinit runs one node per machine. There is no Arch, Nix or Homebrew package.

### Limits by design

- **Disk space** (ADR 0122): one free space limit per node, by default the larger of 1 GiB and 5 % of its volume. Below it, every group with a replica on the node takes no new data, so on a cluster where every group has a replica on every node one low node stops new data everywhere. A node reads its volume every second (`[disk] check_interval_ms`) and reports a change to the metadata group at once, so other nodes refuse within a few seconds; a low node that cannot reach the metadata leader stays as recorded until it can (ADR 0124). It clears only a tenth above the limit.
- **Upgrades** (ADR 0127): a node runs only beside the previous or next minor release, so skipping one means two upgrades. A restart turn does not expire: a node that stays down holds it until an admin gives it back. A turn guards voluntary restarts only; a crash or a restart without a turn is not held back. Whether a group would lose its quorum is judged from what its leader heard within an election timeout, so a node that failed just before is still counted. Until the cluster version is raised, a new release writes the previous release's formats.
- **Retention** keeps whole segments, so a partition holds up to a segment more than its limits; age goes by the timestamps producers write (ADR 0046). A segment closes at its size or at its age, an hour by default, so a log that stops growing frees its space within about that; a restarted node starts the age again, and `segment.ms` is set only through `AlterConfigs`, not at creation (ADR 0146).
- **Storage and reads** (ADR 0094): one `.index` file per sealed segment serves offsets and times; there is no `.timeindex` or `.txnindex`. A node trusts a matching index file on start, so damage inside a sealed segment shows when the batch is read, not at start-up. `ListOffsets` by time answers with a batch, not a record. `Fetch` has no `sendfile`: TLS encrypts in the process, and the response frame copies the data once.
- **Compression** is per batch, zstd and lz4, and a decompressed block may hold at most 16 MiB (ADR 0058). The Java SDK needs zstd-jni and lz4-java on its class path (ADR 0061), the C# SDK the `Lotse.Client.Codecs` package (ADR 0084), and the Node.js SDK brings lz4 itself and uses `node:zlib` for zstd, which needs Node.js 22.15 or later (ADR 0085). `lotse-client` compresses only what the caller builds compressed.
- **Idempotent producers:** a partition forgets a producer after a day without a write, and a retry after that is taken as new; while it knows 10,000 producers it refuses new ones with `PRODUCER_LIMIT` until one is forgotten (ADR 0110). A plain idempotent producer's id survives a client restart only with a producer name, which fences the earlier instance but does not deduplicate a batch the application sends again (ADR 0071).
- **Transactions and groups:** one coordinator group serves all transactional ids and all consumer groups; a heartbeat that changes a group writes only the members it changes, so a member's step in a rebalance writes one member, while a join, leave or expiry writes every member whose target moved (ADR 0125). A transactional queue ack names at most 10,000 messages. Settled queue offsets stay in the ack index as ranges, even below the log start; aborted ranges are dropped once their marker is below it (ADR 0094). Ids live in a tenant (ADR 0062); a tenant deleted and created again is a new incarnation whose ids start afresh (ADR 0069).
- **Publishing** outside a transaction routes by the bindings the node has applied and writes each queue in turn: not atomic across queues, and a publish whose answer is lost is reported as unknown, not sent again (ADR 0079). Inside one the client routes, with bindings it may have cached for up to `metadata_max_age` (ADR 0032). One message per publish.
- **Queue deliveries** are written before they are pushed, one batch per subscription and round (ADR 0109). A new message commits together with its checkout, but only plain data: behind transactional data, a marker or dead letters the leader waits until they are applied (ADR 0111). A delivery from a backlog waits for its checkout's commit. A new leader orders priority levels by offset until it has read the backlog, 1 MiB a round (ADR 0078).
- **Queues:** dead-letter queues and message TTL are per-queue settings, and a retired message is dropped when no dead-letter queue is set (ADR 0055). A length limit (`max.length`, `max.length.bytes`) counts what waits for delivery, not what consumers hold, so a consumer with a large credit lets a queue hold more; a new leader refuses while it reads the queue's backlog; `QUEUE_FULL` after a lost answer leaves the outcome unknown; `drop-head` without a dead-letter queue drops the oldest messages (ADR 0118). Delayed delivery counts whole milliseconds of the leader's clock, and a waiting message holds the ack floor (ADR 0077).
- **Deleted resources:** a tombstone stays in the metadata state until every node the cluster lists has removed its groups' files, so a listed node that is down holds the tombstones made since it last answered (ADR 0100).
- **Changes reach brokers one by one:** right after a change some brokers do not know it yet; a node whose metadata may be behind answers a name it lacks with `NOT_LEADER`, so a named lookup waits for one that caught up (ADR 0145), but `Metadata` without names lists only what the node knows, and the client's lookup of an id by name for admin calls takes the merged answer at once; a removed role binding takes effect on each node once it applies the metadata group; a conditional delete (`if_empty`) checks first and deletes after, so a message produced in between goes with the resource (ADR 0063).
- **Reads in a zone** (ADR 0104, ADR 0116, ADR 0141): a client sees its own writes, but not those of another client whose answers it never saw, which a follower may serve up to `follower_max_lag` (10 s) late. `Metadata` is answered from any node's applied state and never refused, so a resource just created may be missing from it for a moment; clients retry until it shows. Writes still go to the leader. A client without a zone, and any read without `read_at_least`, can still get a stale answer from a leader deposed without knowing it, for up to about two election timeouts (longer if its process pauses); ReadIndex or leases for these reads would close that, and they belong on the same `read_at_least` path. A login that a node in the zone denies, one that has not applied a credential just created, leaves the client's fatal error set although the read then succeeds at the leader, so a later operation that has to retry once can report an authentication error for valid credentials.
- **Certificates:** the CRL file is copied to every node by the operator (ADR 0060), and revoking a client certificate by issuer and serial (ADR 0090) does not cover node certificates. The inventory lists only the client certificates nodes accepted, its "last seen" is up to an hour late, and it does not show certificates revoked only in the CRL file (ADR 0091). A request lapses after 7 days, and at most 256 are held, of them at most 192 that users asked for in their own name, one pending each (ADR 0092, ADR 0119). A certificate signs in without IdP groups, so it grants only roles bound to the user's name. Renewal over a connection (ADR 0123) needs the renewal CA's key on every node and works only in a certificate's window, its last 30 days or past two thirds of its validity; a renewed certificate lasts 90 days, at most 4,096 still valid are held at once, and one used before its record reaches a node is closed there until it does. The old certificate stays valid until it expires.
- **Leadership moves after a crash.** A stopped node hands its groups over first (ADR 0114), and a new group starts on its preferred node (ADR 0095). A crash, or an election that a node short of CPU loses, still moves leadership the way every single-leader broker does: clients wait an election timeout (1 to 2 s by default, ADR 0144), meet `NOT_LEADER` with the new leader and subscribe again, and once more when the group goes back to its preferred node a minute after that node has caught up, longer after repeated elections (ADR 0113). A consumer keeps its messages and its transaction across a move (ADR 0109), and what it never received goes to others at once (ADR 0112); one that does not come back within the queue's resume window (30 s by default) has its messages given to others, unless it closed. `DescribeMetrics` names a leader only while a quorum answers it, so for a moment after an election no node may.
- **Nodes:** four groups move at a time, each as a full copy through Raft, whether a drain, rebalancing, a changed `replication.factor` or a placement (`ReassignPartition`) moves them (ADR 0115); a placed partition is left out of rebalancing, so nodes may stay further apart; rebalancing moves by replica count and uses size only to choose which group goes, so nodes with equal counts and very different sizes stay as they are, and traffic is not weighed (ADR 0052). A drained node exits by itself, even one that was down or cut off during its drain, and must join under a new id to come back (ADR 0051, ADR 0105); one that cannot reach any node it lists keeps running until it can.
- **Console:** chart history (about 10 KiB per stream or queue for 24 h) covers only what the sampler may see (ADR 0045).
- **The operator's endpoint** (ADR 0117) answers one request per connection, at most 32 at once. `/metrics` reports each node's own view, so a cluster's picture is the sum of every node's scrape. `/readyz` is 503 on every node while a group has no leader anywhere, so a Service has no endpoints for that time. `/safe-to-stop` trusts what the leaders heard within an election timeout and does not count a group whose only voter is the node.
- **Native protocol:** keys 0 to 68 except 18, which is free because queue acks join a transaction through `Ack` (ADR 0075), plus the internal `WriteTxnMarkers`; keys 43 to 46, 54 and 61 to 63 are internal too.
