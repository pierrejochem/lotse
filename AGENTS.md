# AGENTS.md

Project memory for everyone who changes this repository: people and AI coding agents alike, whatever the tool. Tool-specific files (`CLAUDE.md`, `.claude/`) only point here. When something here is wrong or missing, fix it here, in the same change.

## What Lotse is

A message broker in Rust: RabbitMQ-style reliable queues and Kafka-style persistent streams on one replicated log, with exactly-once delivery. Read [docs/design.md](docs/design.md) (German) for the design and [docs/adr/](docs/adr/) for why each decision was made. The design document describes the current system; ADRs keep the reasons.

## Commands

```sh
cargo fmt --all                                            # format (max_width 120)
cargo clippy --workspace --all-targets -- -D warnings      # lint; must be clean
cargo test --workspace                                     # all unit tests and short simulations
LOTSE_SIM_SEEDS=5000 cargo test -p lotse-sim -p lotse-server --release   # simulations at CI depth
LOTSE_SIM_SEED=1234 cargo test -p lotse-sim                # reproduce one failing seed exactly

cd console/web && npm ci && npm run build && cd ../..       # build the web app (needed before the console binary)
cargo run -p lotse-console -- --config console/lotse-console.example.toml
make dev                                                  # local dev environment: web app, three nodes, console on 127.0.0.1:8080 (`make` lists all targets)
cargo run -p lotse-node -- check --config cluster.toml       # the node binary: check, certs, run --node <id>
cargo deb -p lotse-node                                    # the Debian package (cargo install cargo-deb)
docker build -f packaging/Dockerfile -t lotse .             # the image
cd console/web && npm run api                              # after changing an API type in Rust: regenerate openapi.json + TS client
cd console/web && npm run typecheck && npm test
make sdk-test                                              # vectors drift check, then the Java SDK, Kotlin layer, C# SDK and Node.js SDK tests (needs a JDK 17+, the .NET SDK of sdk/csharp/global.json and Node.js 20+; LOTSE_BIN=<lotse executable> adds the TLS and real-node tests)
make sdk-csharp-test                                       # only the C# SDK (dotnet test Lotse.sln)
make sdk-node-test                                         # only the Node.js SDK (npm ci, compile, node --test)
mdbook build docs/guide                                    # the guides (cargo install mdbook); output in docs/guide/book
make sdk-vectors                                           # after changing a message or the batch format: regenerate sdk/conformance
cargo clippy -p lotse-proto --all-targets --features samples -- -D warnings   # also lints the vectors example
```

CI (`.github/workflows/ci.yml`) runs on pull requests and pushes to `main`: format, clippy, tests, the web app build with an OpenAPI drift check, a packaging job that builds, installs and checks the Debian package and builds the image, and an SDK job that runs `make sdk-test` with `LOTSE_BIN` set to the `lotse` it builds (Java tests with and without the codecs, TLS and real-node tests, the Kotlin layer's tests, the examples, the C# tests with and without the codecs package, the Node.js tests on Node.js 24), plus a job `sdk-node-20` that runs the Node.js tests on Node.js 20; `main` takes a change only through a pull request with those four jobs green ([ADR 0082](docs/adr/0082-simulations-run-on-pull-requests-and-merging-needs-green.md)). The simulations at depth run only in the release workflow (`.github/workflows/release.yml`): on a version tag, the nine simulation jobs (`simulation` and the client, queue, group, metadata, access, retention, compaction and membership simulations) run at 5,000 seeds each, and nothing is built or published unless all of them pass; run by hand on a branch, it runs the simulations only ([ADR 0088](docs/adr/0088-simulations-gate-the-release.md); depths from [ADR 0027](docs/adr/0027-client-simulation-depth-in-ci.md), [ADR 0030](docs/adr/0030-client-simulation-in-its-own-ci-job.md), [ADR 0031](docs/adr/0031-queues-first-cut.md), [ADR 0033](docs/adr/0033-consumer-groups-first-cut.md), [ADR 0034](docs/adr/0034-metadata-group.md), [ADR 0039](docs/adr/0039-tenants-and-roles.md), [ADR 0046](docs/adr/0046-retention.md), [ADR 0048](docs/adr/0048-adding-and-removing-nodes.md), [ADR 0049](docs/adr/0049-packaging.md), [ADR 0067](docs/adr/0067-log-compaction.md), [ADR 0083](docs/adr/0083-client-sdks-for-csharp-and-nodejs.md)). So a pull request does not run the simulations: run the ones your change touches yourself, at CI depth where it matters, or run the release workflow by hand on the branch. Keep both green.

## Rules that are not negotiable

1. **Nothing above `lotse-rt` touches the real world directly.** No `Instant::now`, `SystemTime::now`, `std::thread`, OS randomness or ambient Tokio APIs; take a `Clock`, `Disk`, `Spawn` or `Rng`. No `HashMap`/`HashSet`: iteration order would make simulations unrepeatable; use `BTreeMap`/`BTreeSet`. `clippy.toml` enforces most of this. ([ADR 0006](docs/adr/0006-tokio-behind-a-runtime-seam.md))
2. **`unsafe` is forbidden** (workspace lint).
3. **Raft core stays sans-I/O.** `lotse-raft` never does I/O; drivers persist a `Ready` in its documented order: snapshot, truncate, entries (synced), hard state, apply, send ([ADR 0023](docs/adr/0023-persist-the-hard-state-after-the-log.md)).
4. **Never weaken a check to make a test pass.** A failing simulation seed is a bug until proven otherwise; find the cause, then decide whether the code or the check is wrong, and say which in the commit.
5. **Safety rules are mutation-checked.** When you add or change a rule that safety depends on, break it on purpose and confirm a test fails; if none does, add one (simulation, or a deterministic unit test for timing-dependent rules). ([ADR 0010](docs/adr/0010-deterministic-simulation-and-mutation-checking.md))
6. **A changed decision gets an ADR.** New or superseded decisions go to `docs/adr/` (copy `template.md`, next number, add it to the index) in the same change, and the design document is updated to match.
7. **No plaintext by accident.** A `TokioRuntime` uses the network only after `with_tls` or `plaintext_on_loopback`; plain TCP is refused off loopback. When the network verifies peers, a node hears only members of its configuration, each only for itself ([ADR 0037](docs/adr/0037-tls-and-node-identity.md)).
8. **The user acts as themselves.** The console never gets its own admin rights; every action uses the signed-in user's identity ([ADR 0019](docs/adr/0019-management-console-on-a-dedicated-node-with-the-user-s-identity.md)).

## Conventions

- **Language:** code, comments, docs and commit messages in English. The design document is German; keep it German when editing it.
- **Comments** explain why, not what. Public items have doc comments (`missing_docs` is on in library crates).
- **Errors** use `thiserror`; messages say what happened and, where useful, what to do.
- **Tests:** unit tests next to the code (`mod tests;` in `tests.rs`), simulations in `crates/lotse-sim/tests/` or a crate's `tests/`. Simulations take seeds from `lotse_sim::check_seeds` and print the seed on failure; scenario tests whose value does not grow with seeds use `check_few_seeds`. A simulation's oracle is written in the test, never borrowed from the code it checks.
- **UI copy and docs** follow the brand voice in [docs/brand](docs/brand/README.md): calm, exact, short; units always named; no hype, no exclamation marks, no emoji. UI colours, type and spacing come from [docs/brand/tokens.json](docs/brand/tokens.json).
- **Commits:** imperative subject line, a body that explains why. The author is the human maintainer; do not add AI co-author or session trailers.
- **Dependencies** go through `[workspace.dependencies]`. Prefer few, well-known crates.

## Working with the maintainer

- Open design decisions are put to the maintainer **one at a time**, each with a recommended option and its trade-off, not as a batch.
- Report results plainly: what changed, what was verified and how, what is still open. If a check was not run, say so.

## Current state and next steps

Built and tested: runtime seam, record format, segmented log, the Raft core (elections with optional pre-vote and mandatory check-quorum, snapshots, learners, joint consensus, leader transfer, ReadIndex and optional leases, probing after a conflict ([ADR 0102](docs/adr/0102-a-leader-probes-after-a-conflict.md))), the simulation harness, and the management console against real clusters and a built-in demo cluster.

`lotse-server` has `Replica`, a durable Raft group on `lotse-log`, and `Node`, which runs many groups over one transport with Multi-Raft batching ([ADR 0025](docs/adr/0025-frame-oriented-network-seam-and-raft-wire-format.md)) and serves clients over the first cut of the native protocol: `ApiVersions`, `Metadata`, `Produce`, `Fetch` ([ADR 0026](docs/adr/0026-native-protocol-first-cut.md)). `lotse-client` speaks it. `lotse-rt-tokio` runs everything on real disks and TCP. Produce is idempotent: producer ids from a coordinator group, sequences checked against the whole log, producer state in snapshots ([ADR 0028](docs/adr/0028-idempotent-producers.md)); `lotse-client` uses it by default, and a producer with a name gets its id from the coordinator like a transactional id, so a restart fences the earlier instance ([ADR 0071](docs/adr/0071-named-idempotent-producers.md)). Transactions work end to end: coordinator records in the coordinator group, markers through the internal `WriteTxnMarkers`, an epoch raised per transaction, last stable offset and aborted ranges in the replica (dropped once their marker is below the log start, ADR 0094), read_committed in the client ([ADR 0029](docs/adr/0029-transactions.md)). A partition leader takes a producer's first transactional batch of an epoch only after the coordinator confirms, with the internal `VerifyTxn`, that the transaction is open and holds the partition, so a client that skips `AddPartitionsToTxn` cannot hold back the last stable offset ([ADR 0057](docs/adr/0057-partitions-verify-transactions-with-the-coordinator.md)). Batches may compress their record block with zstd (libzstd) or lz4 (`lz4_flex`), at most 16 MiB decompressed; the leader decodes a compressed batch once when it is produced and refuses one that does not decode, and everything after stores and serves it compressed ([ADR 0058](docs/adr/0058-zstd-and-lz4-compression.md)). Queues work: acks and delivery counts as batches in the queue's log, applied into an ack index in every replica; the leader pushes deliveries within each subscription's credit, after it has applied an entry of its own term and below the last stable offset; redelivery after nack, disconnect, failover and the ack timeout; consumers in the client ([ADR 0031](docs/adr/0031-queues-first-cut.md)). Durability, segment index, retention, compaction, membership, transport, protocol, idempotence, transaction, queue, transactional ack, single active consumer, delayed delivery, priority, routing, publish, group, metadata, node-link, certificate revocation, authentication, authorization and console sign-in rules are mutation-checked. Publishing goes through exchanges: outside a transaction `Publish` (key 9) goes to any node, which routes by the bindings it has applied, checks the publisher's producer role on the exchange and every routed queue, and writes each queue with an idempotent producer of its own; a lost answer is reported as unknown, not sent again ([ADR 0079](docs/adr/0079-publish-routed-by-the-node.md)), while an entry refused by a node that has not heard of the exchange yet (`NOT_LEADER`, nothing written) is sent again ([ADR 0101](docs/adr/0101-a-publish-refused-by-a-node-behind-is-sent-again.md)); inside a transaction the client routes and produces to each queue atomically ([ADR 0032](docs/adr/0032-publish-routed-by-the-client.md)). The Java SDK publishes through `LotseClient.publish`. Consumer groups work: membership and assignments persisted in the coordinator group, cooperative rebalancing so no partition has two owners, offsets committed plainly or within a transaction for exactly-once consume-transform-produce ([ADR 0033](docs/adr/0033-consumer-groups-first-cut.md)). A member with an instance id keeps its place when it leaves, until its session times out, and the next instance with that id takes it over with its partitions and no rebalance; an earlier instance gets `FENCED_INSTANCE_ID` and stays out ([ADR 0072](docs/adr/0072-static-group-membership.md)). A member may subscribe by a regular expression, which the coordinator matches with every heartbeat against the streams of the group's tenant the member may read, so new streams join in ([ADR 0073](docs/adr/0073-pattern-subscriptions.md)). `ListOffsets` gives a partition's start, the end a reader sees, or the first batch at or after a time (segments' newest timestamps, then the segment's index and a scan of at most one index interval of batch headers, [ADR 0094](docs/adr/0094-segment-index-files-and-reads-without-copies.md)), and a group starts a partition without a committed offset where `GroupConfig::start_from` says ([ADR 0059](docs/adr/0059-list-offsets.md)). A metadata group creates streams, queues and exchanges and binds queues at runtime (`CreateStream`, `CreateQueue`, `DeclareExchange`, `Bind`, `Unbind`), placing each new group on as many nodes as asked; configured resources stay ([ADR 0034](docs/adr/0034-metadata-group.md)). Runtime resources can be deleted (`DeleteResource`: a tombstone in the metadata state; every replica closes the group and removes its files; the tombstone goes once every listed node reports, through `DescribeMetrics`, that it removed the files, and the id stays deleted without it, [ADR 0100](docs/adr/0100-tombstones-go-once-every-node-removed-the-files.md)) and a queue's ack timeout changed and read (`AlterConfigs`, `DescribeConfigs`) ([ADR 0035](docs/adr/0035-deleting-resources-and-changing-settings.md)); with `if_empty` the metadata leader first asks every partition's leader (the internal `CheckEmpty`) and deletes only what holds nothing ([ADR 0063](docs/adr/0063-conditional-delete.md)). A runtime stream's partition count can be raised (`CreatePartitions`): new partitions are placed like a new stream's, keep the stream's index in their group ids, and consumer groups spread over them on their next heartbeat ([ADR 0074](docs/adr/0074-adding-partitions-to-a-stream.md)). Every node answers `DescribeMetrics` for itself: running totals (traffic, produces, fetches, deliveries, acks), a commit latency histogram, its groups, led queues and consumer groups, and the host through the `Host` seam; the console (`kind = "native"`) asks every node and turns counters into rates ([ADR 0036](docs/adr/0036-describemetrics-and-the-console-against-a-real-cluster.md)). Every connection speaks TLS 1.3 with certificates from the cluster's CA; node links need node certificates (`lotse://node/<id>`) on both ends, and plain TCP is allowed only on loopback when asked for ([ADR 0037](docs/adr/0037-tls-and-node-identity.md)). Handshakes check a revocation list (`[tls] crl`), a running node takes up changed certificate files every 10 s and ends the connections of certificates the new list revokes, and `lotse certs` issues certificates for a year (CA ten) and revokes with `--revoke` ([ADR 0060](docs/adr/0060-certificate-renewal-and-revocation.md)); a cluster admin revokes a client certificate by issuer and serial through `RevokeCertificate`, recorded in the metadata group and checked by every node's session, which ends the connections that showed it (`Conn::peer_cert`; node certificates stay with the CRL file, [ADR 0090](docs/adr/0090-revoking-client-certificates-in-the-metadata-group.md)); nodes report the client certificates they accept (`RecordCertificates`, internal) and a cluster admin lists them with their state (`DescribeCertificates`, [ADR 0091](docs/adr/0091-client-certificate-inventory.md)); a cluster admin asks for a client certificate with a signing request made in the browser (`RequestCertificate`, `DescribeCertificateRequests`) and the CA holder signs it offline with `lotse certs --sign`, which records the certificate (`RecordCertificate`): the cluster and the console hold no private key and no CA key ([ADR 0092](docs/adr/0092-requesting-and-signing-client-certificates.md)); the metadata leader takes a recorded certificate only if it has the request's key and principal, is signed by a CA certificate of `[tls] ca` and says what the record says, and an issuer is named by its name and authority key identifier, so two CAs with one name are two issuers ([ADR 0096](docs/adr/0096-recorded-certificates-are-checked.md)); a connection ends when the certificate its other end showed expires ([ADR 0068](docs/adr/0068-connections-end-when-their-certificate-expires.md)). Clients authenticate with a certificate, SASL SCRAM-SHA-512 (credentials in the metadata group, `AlterUser`, `DescribeUsers`) or SASL OAUTHBEARER (tokens checked against the issuer's keys, fetched through the `Http` seam); sessions end and clients renew them ([ADR 0038](docs/adr/0038-authentication.md)); a cluster admin revokes a user's or IdP group's sessions (`RevokeSessions`): connections whose credential predates it close and older tokens are refused ([ADR 0070](docs/adr/0070-revoking-sessions-by-principal.md)). Tenants are created explicitly and every resource belongs to one; six roles (cluster-admin, cluster-viewer since [ADR 0043](docs/adr/0043-cluster-viewer-role.md), tenant-admin, producer, consumer, viewer) are bound to users or IdP groups per tenant and name prefix in the metadata group, with bootstrap admins from the configuration; every request is checked, and what a principal may not see is unknown to it ([ADR 0039](docs/adr/0039-tenants-and-roles.md)). Transactional and consumer group ids live in a tenant too: requests name it as a tag (absent: `default`), the ids are checked against the producer and consumer roles with the binding's prefix, and the coordinator keys them by tenant ([ADR 0062](docs/adr/0062-transactional-and-group-ids-live-in-a-tenant.md)) and its incarnation, the index that created it, so a tenant created again starts afresh and the coordinator leader forgets the old incarnation's ids with a `Forget` record ([ADR 0069](docs/adr/0069-tenant-incarnations.md)). A simulation in its own CI job checks that nothing is allowed that no binding allowed while bindings change under faults. The console signs users in with OpenID Connect (Authorization Code with PKCE, sessions on the console, the access token passed on with OAUTHBEARER) or in dev mode with a SCRAM password, and keeps one client per principal, so each user sees what their roles allow ([ADR 0040](docs/adr/0040-console-sign-in.md)); it purges queues (the name typed again), requeues dead letters and pins leaders as the user ([ADR 0066](docs/adr/0066-console-actions.md)), and manages users, role bindings and session revocation the same way, with passwords derived in the browser so the console never sees one ([ADR 0089](docs/adr/0089-console-users-and-access.md)); sessions are sealed into the cookie (AES-256-GCM, a key the console makes once: [ADR 0042](docs/adr/0042-the-console-keeps-its-session-key.md)) and survive restarts, as do sign-ins in progress ([ADR 0044](docs/adr/0044-sign-ins-in-progress-in-a-sealed-cookie.md)), the metrics sampler signs in with client credentials, and charts sum only what the user may see, from history that gets coarser with age ([ADR 0045](docs/adr/0045-chart-history-coarser-with-age.md), [ADR 0041](docs/adr/0041-console-sessions-sampler-sign-in-and-charts-per-user.md)). Logs are trimmed at snapshot points: a replica records a snapshot where applying reaches a segment base and cuts there; streams by age and size (node defaults, per stream at runtime with `retention.ms` and `retention.bytes`), queues below the ack floor, the metadata and coordinator groups at a snapshot of their state, never past the last stable offset; a group member whose position was deleted goes on from the log start ([ADR 0046](docs/adr/0046-retention.md)). Streams created with `cleanup.policy = compact` (or `compact,delete`) are compacted by each replica on its own: sealed segments below the last stable offset are rewritten whole, batches keep their offsets, term and producer fields and lose the records a newer one of their key replaces, aborted ones, and tombstones older than `delete.retention.ms`, which only a leader drops and only below what every member holds; attribute bit 8 marks a compacted batch, which the Rust client and the Java SDK read ([ADR 0067](docs/adr/0067-log-compaction.md)); a sweep maps at most `[compaction] map_bytes` of key hashes (16 bytes of SHA-256) from where the last one's map ended, and a node runs one sweep at a time ([ADR 0098](docs/adr/0098-compaction-maps-a-bounded-number-of-keys-per-sweep.md)). The `lotse` binary runs one node from a cluster file the same on every node (nodes, TLS paths, retention defaults, authentication; no resources: clients create them), every node a voter of the metadata (1) and coordinator (2) groups; `lotse certs` makes the CA and node and client certificates and signs requests with `--sign` ([ADR 0047](docs/adr/0047-the-lotse-binary.md)). Nodes come and go at runtime: the node list lives in the metadata group (`AddNode`, `RemoveNode`, `DescribeNodes`), nodes follow it with their links, a joining node starts outside the configured groups (`join`, `first-voters` on disk), the metadata leader plans each group's voters (`SetVoters`: drained nodes replaced, at most four groups moving, metadata and coordinator groups at up to five voters, every other node a learner of the metadata group), each group's leader carries them out through learners and joint consensus, tagging the membership with the decision's index, and reports them (`SettleVoters`) before old replicas are removed ([ADR 0048](docs/adr/0048-adding-and-removing-nodes.md)). Queues can limit deliveries (`max.deliveries`), expire messages (`message.ttl.ms`) and dead-letter them into another queue of the tenant (`dead.letter.queue`), per queue, off by default: the leader claims a message in a `RETIRE` batch, forwards it with the internal `DeadLetter` request, and the receiving queue recognises repeats, so a move happens once across failovers ([ADR 0055](docs/adr/0055-dead-letter-queues-and-message-ttl.md)); tenant admins purge a queue's ready messages (`PurgeQueue`) and requeue a dead-letter queue's messages to their source the same way back (`Requeue`) ([ADR 0064](docs/adr/0064-purge-and-requeue.md)). A consumer acks queue messages within a transaction (`Ack` with a transactional id, on the connection they came on, after `AddPartitionsToTxn` adds the queue; `Consumer::ack_in`): the leader takes them out of flight, a transactional ack batch makes the transaction hold them in every replica's ack index, the commit marker settles them and the abort marker gives them back, so consume-transform-produce from a queue is exactly once; of two transactions the first in the log holds a message and the other gets `MESSAGE_NOT_HELD`, and acks alone do not hold the last stable offset back ([ADR 0075](docs/adr/0075-queue-acks-in-transactions.md)). A queue with `single.active.consumer = true` delivers to one subscription at a time: the others wait as standbys in the order they subscribed (`standby` in the answer, a push when it is their turn if they asked), and the oldest takes over only once nothing is out with anyone (in flight, held back for a count, held by a transaction), so the queue's order holds across the handover; leader-local ([ADR 0076](docs/adr/0076-single-active-consumer.md)). Messages wait for their time: a producer asks with the header `x-lotse-delay-ms`, counted from the leader's append time (every queue batch now carries the leader's clock), and a requeueing `Nack` with `delay_ms` (`Consumer::nack_after`) writes a TIMER batch that every replica keeps until the message settles; the leader defers what is not due and delivers it first once it is ([ADR 0077](docs/adr/0077-delayed-delivery.md)). A queue with `priority.levels` (2 to 10) keeps one log: the leader reads each message's `x-lotse-priority` header as data becomes deliverable (a new leader reads the backlog, 1 MiB a round) and hands out the highest level first, by offset within a level, without moving the cursor past the level-0 messages it overtakes ([ADR 0078](docs/adr/0078-queue-priorities.md)). Packages ([ADR 0049](docs/adr/0049-packaging.md)): a static image on distroless, `lotse@.service` with sandboxing, a Debian package (`cargo deb`), and a release workflow on `v*` tags (static x86_64 and aarch64 binaries, packages, checksums, `ghcr.io/<owner>/lotse`); a node reads `LOTSE_NODE`, `LOTSE_CONFIG` and `LOTSE_JOIN` when no flag says otherwise. Groups spread over the nodes by themselves ([ADR 0050](docs/adr/0050-rebalancing-groups-onto-new-nodes.md)): while no node drains, the planner moves one replica at a time from the fullest node to the emptiest until they are within one replica or a tenth, and each group's leader hands leadership to a preferred voter computed the same on every node; a moved replica keeps only its term and vote, so a group may return to a node, and a node with a lagging view keeps a replica whose membership is newer than the move; a move settles only once committed, and a node runs a replica it was moved off until then; a cluster admin pins a partition's leader to one of its voters (`MoveLeader`, a pin in the metadata state that the spreading leaves alone, [ADR 0065](docs/adr/0065-pinned-leaders.md)); Raft ignores answers from before a member joined and lets a learner that lost its log start over; a node whose metadata leader it does not list asks for the node list and hears those nodes for the metadata group only. A new group's preferred replica campaigns at its first tick and the others wait one election timeout more, so a new group starts on its preferred node and is not handed over; `DescribeMetrics` names a leader only while a quorum answered it within an election timeout ([ADR 0095](docs/adr/0095-a-new-group-starts-on-its-preferred-node.md)), and a queue leader hands out messages only then ([ADR 0097](docs/adr/0097-a-queue-leader-delivers-only-with-a-recent-quorum.md)). Snapshots travel in chunks, one in flight per follower, installed only with the last ([ADR 0053](docs/adr/0053-snapshots-travel-in-chunks.md)); the core hands each chunk to the replica, which writes it to a file, and a replica keeps every snapshot (latest, boundaries, those in transfer) in files and sends chunks read from them ([ADR 0099](docs/adr/0099-snapshots-live-in-files.md)). A drained node stops by itself and `lotse run` exits 0, whether its own metadata state shows it drained or the metadata leader no longer lists it ([ADR 0051](docs/adr/0051-a-drained-node-stops.md)); the latter also for a node that never saw its drain, from an answer at least as new as its own state, which still lists it (`DescribeNodes` with the internal `applied_at_least`, [ADR 0105](docs/adr/0105-a-forgotten-node-stops-without-seeing-its-drain.md)). When a move is due, the planner takes the group that evens out the two nodes' bytes most, from sizes the metadata leader reads with `DescribeMetrics` ([ADR 0052](docs/adr/0052-rebalancing-weighs-moves-by-size.md)). A JVM client is being built in `sdk/` in phases (ADR 0056); the protocol codec and record batch in Java exist and are tested against the Rust vectors, connections (TLS 1.3, pipelining, pushes, sessions) and SCRAM/OAUTHBEARER authentication exist too, and the stream client (`LotseClient`: metadata routing with leader hints, idempotent produce, read_committed fetch, `createStream`) and the queue consumer (`subscribe`, `QueueConsumer`: credit, ack and nack, delayed requeue with `nackAfter`, standbys of a single active consumer, resubscribing, dead-letter headers, `createQueue`) follow `lotse-client` rule for rule and are mutation-checked; it reads and writes zstd and lz4 batches through zstd-jni and lz4-java, optional dependencies whose absence it names ([ADR 0061](docs/adr/0061-optional-codecs-in-the-java-sdk.md)); transactions (`beginTransaction`: produce, publish routed in the client with routing checked against `sdk/conformance/routing.txt`, queue acks with `ackIn`, group offsets with `sendOffsets`) and consumer groups (`joinGroup`, `GroupConsumer`, heartbeats from `poll` as in Rust) follow the Rust client rule for rule and are mutation-checked, as do the admin calls (exchanges, bindings, deletes, settings, purge and requeue, users, tenants, roles, nodes, pins, partitions, sessions, metrics); and `sdk/kotlin` wraps it for coroutines: every call a `suspend` function on `Dispatchers.IO`, reads as flows, and `transaction { }`, which commits when its block returns and aborts on an exception or cancellation ([ADR 0080](docs/adr/0080-kotlin-layer-on-dispatchers-io.md)); examples in `sdk/java/src/examples` and `sdk/kotlin/src/examples` are compiled by `check`, and CI runs `make sdk-test` (phase 8). The C# client in `sdk/csharp` and the Node.js client in `sdk/node` ([ADR 0083](docs/adr/0083-client-sdks-for-csharp-and-nodejs.md)) cover the same scope as the Java client (streams, queues, publishing, transactions, consumer groups, admin, TLS, SCRAM-SHA-512, OAUTHBEARER), follow it rule for rule, pass the golden vectors and are mutation-checked; their zstd and LZ4 support is optional ([ADR 0084](docs/adr/0084-codecs-in-the-csharp-sdk.md): the `Lotse.Client.Codecs` package; [ADR 0085](docs/adr/0085-codecs-in-the-nodejs-sdk.md): lz4 in the SDK, zstd from `node:zlib` on Node.js 22.15 and later).
